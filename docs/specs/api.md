## 0. 通用约定（**接入前必读**）

| 项 | 约定 |
|---|---|
| 字符编码 | **全部 UTF-8**。请求体必须声明 `Content-Type: application/json; charset=utf-8` |
| 中文查询参数 | 走 GET 的 `q`/`modules` 时必须 **UTF-8 percent-encode** |
| 错误格式 | FastAPI 标准 `{"detail": "..."}`；`detail` 是**中文业务说明**，可直接展示给用户 |
| 外发 | **三条外发路径，服务端硬开关默认全 `false`，未授权路径明确 403（不静默降级）**：① §5 方案生成（外发我方响应正文）；② §1A 的**意图识别兜底**（只外发**用户自己敲的那一句查询**，且**本地优先、判不出才发**）；③ 白名单 OCR（扫描件，`OCR_ENABLED`；本地 RapidOCR 后端 `OCR_BACKEND=local` 零外发、不受此闸约束）。**其余端点零外发** —— 特别注意 §2B「正文提及」组是**纯本地规则**。每条外发路径均有独立授权记录（`docs/authorizations/`，共 **6** 份，其中第 6 份「合同正文 LLM 语义复核」**暂缓启用、代码无触发路径**），**范围不可自行扩大** |
| 只读 | **无任何写接口**：数据变更走离线脚本，不经 HTTP。⚠️ 唯一的例外是 §7 `POST /api/open` —— 它**不改任何数据**，但会在**服务端所在机器上**启动外部程序（资源管理器／默认程序），默认关闭 |

### ⚠️ 实测踩过的坑（别重犯）

1. **中文参数编码**：用 `curl --data-urlencode` 在 Windows 终端下会被按 **GBK** 编码，
   服务端收到乱码字节 → `400 未知方案小节`。**必须显式用 UTF-8 编码**：
   ```python
   import urllib.parse
   q = urllib.parse.urlencode({"modules": "售后方案,应急预案"}, encoding="utf-8")
   ```
2. **`scheme-search` 的 `limit` 默认是 8**（不是"只有 8 条数据"）。要看更多请显式传 `limit`，上限 30。
3. **`material-search` 的 `hits` 与 `excluded` 要分开看**：`hits` 是符合条件的合同，
   `excluded` 是"为什么没被采用"的解释。**做导出/统计时不要混用**。

## 1A. `GET /api/ask` — 需求一**唯一入口**（2026-09-13 新增）

一句话自然语言 → 服务端自动判断该查四类中的哪一类，再转发对应端点。
**页面 01 的材料定位表单走的就是这个**，产品/金额/日期的规则判断只在服务端一处，不散到前端。

```
GET /api/ask?q=2024年12月之后，代谢组服务金额4万元以上的合同
```

**四类问法与判据（顺序即优先级：材料 → 方案 → 合同）**

| `kind` | 问法示例 | 判据 | 转发到 |
|---|---|---|---|
| `fact` | 「哪些响应文件包含2025年的社保」「哪些文件里有仪器照片」「有哪些发票材料」 | 社保/财务/完税/纳税/仪器/设备/发票/采购合同/照片/资质… | `/api/material-facts` |
| `scheme` | 「以前哪个文件写过售后服务方案」「哪些文件写过应急预案」 | 方案/预案/措施/保密/培训/质控/物流/风险/团队/服务周期… | `/api/scheme-search` |
| `contract` | 「2024年12月之后，代谢组服务金额4万元以上的合同」 | 以上都不含 → 按合同查 | `/api/material-search` |

**为什么材料优先于合同**：「**仪器采购合同**」含「合同」二字，但用户问的是
「有没有采购合同这份材料」；而「**代谢组合同**」不含材料词，落回合同查询。

**响应**统一为对应端点的响应体 + `kind` + `query` + **`recognition`** 三个字段，调用方据此渲染。

**`recognition`（2026-09-16 新增）—— 「系统理解成了什么」的原样回显，接入方应展示它**

| 字段 | 取值 | 含义 |
|---|---|---|
| `intent` | `contract` / `material` / `instrument` / `scheme` / `unknown` | 意图层判定出的类别 |
| `confidence` | 0.0–1.0 | 置信度 |
| `reason` | 字符串 | 判定理由（本地规则或模型给出） |
| `source` | `local` / `llm` / `local_fallback` | 走了哪条路：本地判定 / 模型兜底 / **外发失败回落本地** |
| `decided` | 布尔 | 本地是否**判得出**（`false` = 本地认不出，已/将问模型） |

⚠️ **`kind` 与 `intent` 不是同一个东西**：`kind` 是**实际转发**去的那条路（`fact`/`scheme`/`contract`），
`intent` 是意图层判定（多一个 `instrument`，且可能为 `unknown`）。**不要用 `kind` 反推 `intent`**。
⚠️ **`source=llm` 时实体（产品/金额/日期/厂商）由模型抽出后直接进检索**，不再二次解析原句 ——
二次解析会把已识别实体丢掉（实测「…三十万往上的合同」被中文数字卡住 → 400，而意图层已认出 300000）。
⚠️ **本地优先**：只有本地判不出且 `INTENT_LLM_ENABLED=true` 才会外发，且**只发这一句查询**
（授权见 `docs/authorizations/llm-intent-authorization.md`，不含任何文档正文）；外发失败回落
`local_fallback`，**不静默外发、不因外发失败返回 5xx**。

⚠️ `kind=contract` 时，条件不支持（如「不要宏基因组」里的产品名不在已知别名内、
或只给机构不给金额）会返回 **400 + 中文原因**——这是**故意拒绝**，不是故障：
宁可明确说「这个条件我不认」，也不把条件悄悄丢掉后继续搜。

## 2. `POST /api/material-search` — 需求一：历史材料定位

自然语言 → 合同定位。**这是需求一的主入口。**

**请求**
```json
{"query": "找10万以上的代谢组合同"}
```

**响应**
```json
{
  "parsed": {"product": "代谢组", "minimum_amount": 100000.0, "operator": ">=",             "party_include": [], "party_exclude": [], "product_exclude": []},
  "hits": [ { "contract_id": "CTL-...", "file_name": "...pdf", "product": "代谢组学",
              "amount": 117000.0, "amount_status": "ok", "amount_source": "declared",
              "detail_evidence": "代谢组学 | 例 | 450.00 | 260 | 117,000.00 元",
              "contract_number": "YOE2024114080", "party_a": "...", "party_b": "...",
              "contract_date": "2024-12-02", "total_amount": 369000.0,
              "source_path": "\\\\192.168.10.188\\...", "hit": true } ],
  "excluded": [ { "hit": false, "skipped_reason": "明细来源指纹缺失...", "amount_status": "conflict" } ],
  "filter_note": "", "scope_note": "注意：本页目前覆盖 95 份已核合同。..."
}
```

**必读语义**
- **结果已排序（R6-05，2026-09-13 落地）**：`hits` 按
  **角色（我方响应/最终版）→ 格式（原生 → 混合 → 扫描 OCR）→ 命中 → 金额大 → 签订日新 → 合同号** 排序。
  此前**没有排序层**，结果按 `contract_id` 字典序返回，`Success@5/Precision@10` 因而无定义。
  排序是**确定性**的（同一查询两次运行结果完全一致），评测可复现。
- `amount` 是**该合同里对应产品的金额**，不是合同总额（`total_amount`）。多组学合同里
  代谢只是其中一项，两者不同是**正常的**。
- `amount_source`：`declared` = 合同明写；`derived_qty_x_price` = **由数量×单价推算**。
  **展示时必须标注推算值**，不能与明写值看起来一样。
- `amount_status: "conflict"` = 金额前后对不上 → **不列为符合项**（宁缺毋滥）。
- `source_path` 是真实 NAS 路径，可直接给 IT 定位；**不要**当作可读取的本地路径使用。
- **支持的产品（2026-09-13 扩充，用户确认）共 14 类**：
  代谢组 / 单细胞 / 蛋白组 / 空间转录组 / 空间代谢组 / 脂质组 / 靶向检测 / 宏基因组 /
  全基因组重测序 / ATAC / Xenium / Olink / 多组学 / 转录组。
  ⚠️ 判定是**子串关键词 + 首个命中即返回**，故窄产品排在宽产品前面
  （「空间代谢组」不会被「代谢组」抢走、「单细胞转录组」判为**单细胞**）。
- **排除语义（`product_exclude`）**：`不要X` / `排除X`，X 须是**已知产品名或已知公司名**；
  只要有一个词归不了类，**整条查询被拒**并指出是哪个词（绝不"执行一半、丢掉一半"）。
  主产品的判定会**先摘掉「不要X」子句**再匹配 —— 否则
  `查找1万元以上的蛋白组合同，不要宏基因组` 会先命中「宏基因组」变成
  「查宏基因组、再排除宏基因组」而**恒返回 0 条**（2026-09-13 修复）。
- **金额可省的前提**（都是**收窄**条件，不是放宽）：给了日期，**或**给了机构/排除条件。
  故「乙方是欧易的代谢组合同」现在可用（原先会被要求"请写明最低金额"）。
  三个都没有 → 仍然拒绝。

## 2A. 业绩清单段（`ledger`）—— 2026-09-16 新增，**两条红线**

响应文件里的**业绩清单**（近三年主要项目业绩表）是我方**自己写的声明**，不是合同原件。
它已被抽取为 `LEDGER-*` 行（2026-09-16 从 29 条补到 **126 条 / 16 份**）并进入检索，
但**必须**按下面两条口径返回：

| 红线 | 落地方式 |
|---|---|
| **参与金额筛选（口径已改判）** | 2026-09-16 用户改判「最好让非 pdf 的合同金额也参与金额条件」→ 金额门槛**下沉到业绩行**，用其**合同总额**参与筛选。依据：127 份「有总额且有明细」的 CTL 合同上按 1万/5万/10万/30万/50万 门槛比对，**误返 0 份、漏召最多 2 份**。接入方**必须**仍写明「金额是**业绩表所列合同总额**、非产品明细金额」；未达门槛的见 `excluded_below_amount`（计数）、金额未记载的见 `excluded_no_amount`（**单列文件**，不得静默丢弃） |
| **不混进 hits** | 业绩行永远放在独立字段（不是 `hits`），每条带 `source_label = "业绩清单声明（我方响应文件）"` 与 `amount_note`（写明是合同总额、不参与筛选）；**绝不与合同原件混在同一个列表** |

**出现的位置**：
- `POST /api/material-search` 与 `GET /api/ask`（合同路径）→ 无金额条件时返回 `ledger: {records[], count, truncated, source_label, scope_note}`；
- `GET /api/three-modules?module=项目业绩` → 返回 `ledger_records[]` / `ledger_count` / `ledger_source_label` / `ledger_scope_note`（与合同原件 `records` **并列而不混**）。

**每条字段**：`{contract_id, ordinal, party_a, project, amount, amount_note, evidence_text, relative_path, project_folder, document_id, source_root_id, content_format, document_role, source_label}`。

⚠️ **两条已知语义**：① 业绩行**没有合同编号**（实测 0/126），**无法与合同原件自动对账** ——
不要按合同号去 join；② 查询里的「乙方」**不用于筛业绩行**（查询里乙方=供应商/我方，
业绩行的 `party_a`=采购人/客户，角色不同名同义会误杀）。

## 2B. 「正文提及」合同组（`mention_contracts`）—— 2026-09-17 新增，**展示线索、不参与筛选**

明细里没有目标产品、但**合同正文写着**的合同（判据：产品词 ±12 字内有业务上下文词
测序/检测/分析/服务/组学/样本/项目/实验/建库/上机/合同/委托 之一）。**本地规则、零外发。**
背景与 12 条决策见 `docs/plans/active/PLAN-20260917-contract-product-mention.md`。

**出现的位置**：`POST /api/material-search` 与 `GET /api/ask`（合同路径）→
`mention_contracts: [...]` + `mention_note`（口径说明，接入方应原样展示）。

**三条红线（接入方必须遵守的展示口径）**：

| 红线 | 说明 |
|---|---|
| **永不进 `hits`** | 提及组是独立字段；把它并进合同命中列表 = 放宽门槛造命中 |
| **不参与金额筛选** | 查询里的金额门槛**不作用于**这一组；`total_amount` 是**合同总额**（该产品未单列），必须随 `amount_note` 展示 |
| **必须带依据上屏** | 每条含 `evidence_snippet`（正文依据原文）与可打开的 `source_path`；这是「需人工确认」的线索，不是系统背书的命中 |

**每条字段**：`{contract_id, contract_number, party_a, party_b, contract_date, total_amount,
document_id, relative_path, project_folder, content_format, document_role, file_name,
source_path, product, mention_source, amount_note, evidence_snippet}`。

**排除语义**：`product_exclude` 按**合同级作用于正文**（排除词在正文出现 → 整份合同不进提及组）；
已在 `hits` 命中的 `document_id` 不重复进提及组。

## 4. `GET /api/material-facts` — 需求一 场景2/3：材料存在性

`?q=找2023年的财务报告` 或 `?fact_type=finance_period&fact_value=2023&limit=50`

返回 `{count, facts[], total_available, truncated, related_count, related[], files[], file_count, scope_note}`。

**必读语义**
- **`files` / `file_count`（2026-09-16 新增）是「按文件折叠」的展示口径**：材料事实是**一条期间一行**
  （一份社保缴费记录表有 4 个月 ⇒ 4 条），直接用 `facts` 渲染会把**同一份文件显示多次**。
  `files` 每条 = 原行字段 + `fact_values`（该文件全部期间，按时间序、`null` 排最后）+ `record_count`。
  **`facts` 保留不变**（向后兼容）；新接入方**应渲染 `files`**：`file_count` 说「**几份文件**」、
  `count` 说「**几条记录**」—— 两者**不是一回事**，不得混用（业务问的是「哪几份文件能用」）。
- **`truncated` 必须展示**：`limit` 默认 50、上限 500，超出会**静默截断**。
  实测「社保」库内 1,182 条 —— 不显示 `total_available` 的话，页面看起来就是「只有 50 条」。
- `related` 是**期间语义为「起始」**的条目（如 `'2021~'`，未记终期）。
  按**月**查询返回 0 是**如实的**，不是 bug——`scope_note` 会说明。
- **`content_snippet` / `snippet_source` / `snippet_missing`（2026-09-17 新增）= 「可复制正文段」**：
  需求方第二次对接的主诉是「原件都有，但要定位到文件里**整理后的、可以复制的内容**」。
  后端按**材料自身标题**（`app.api.SNIPPET_ANCHORS`，如 `社会保险费缴费记录`/`完税证明`/`仪器设备清单`）
  在**响应文件正文**里定位，裁出**原样段落**（限 600 字，含材料标题之后的内容）。**只读、零外发、不改库**。
  ⚠️ 三条口径：① 锚点**只用材料自身的标题/表名**，不用泛词 —— 松锚点会把「招标要求句」当材料
  （那是放宽条件造命中）；② 裁不到 → `snippet_missing=true` 且 `content_snippet=""`，
  接入方**必须如实说明「正文里没找到该类材料段落」**，**不得用文件名冒充内容**；
  ③ 这是**原文摘录**（可直接粘进标书），但不是「已核材料」——仍受 `role_scope` 约束（见下条）。
- **排序（2026-09-17 变更）**：材料事实行按 **空壳行沉底** 排序（`app.api.SHELL_ROW_SQL`：
  无 `fact_value` 且 `evidence_text` 只有 `[角色] 文件名` 的行排最后）。
  改前实测 211 条「无型号无正文」的仪器行**排在有内容行之前**，用户看到「定位到了文件但什么都没有」。
  ⚠️ 该 SQL 判据与 Python 的 `_annotate_fact_role` **必须等价**（有回归测试钉住 1,986 行零错分）。
- **`fact_type` 新增合法值 `finance_amount`（2026-09-17）**：「凭证合计金额」——
  从完税证明/社保完税凭证的**合计行**抽出（判据见 `app.extract.find_voucher_total`：
  必须有税务/社保机构痕迹 + `金额合计`/`价税合计` 等锚点；**不扫全文找数字、不按明细求和**）。
  `fact_value` 是金额字符串（元）。实库覆盖 **29 条 / 19 份凭证**。
  ⚠️ **社保缴费记录表（`社会保险费缴费记录`）没有合计行 → 一律抽不到**，如实不产出，
  **不按明细求和**（同一份表里养老/医疗/失业/工伤不可加总成「社保总额」）。
  查询映射：`纳税社保总金额` / `社保总金额` / `完税总额` → `finance_amount`
  （**必须排在「社保」之前**，否则会落到 `social_security_month` 那一类**期间**上）。
- **条目「无值」的说法按类别取（2026-09-18 修）**：`fact_type` 决定那一行到底该显示什么 ——
  `social_security_month` / `finance_period` 是**期间**；`instrument_name` 是**型号**；
  `finance_amount` 是**金额**；而 `instrument` / `invoice` / `qualification` /
  `purchase_contract` / `instrument_photo` **五类存的是「存在性」**（有没有这类材料），
  `fact_value` **恒为空**。接入方**不得**对后五类显示「期间未提取到」（读起来像系统故障）。
  实库：这五类共 **556 行**，`fact_value` 非空数 **0**。
- **`q` 解析不出条件时返回空集 + 明确说明（2026-09-18 修）**：原先会**落回全表**
  （`q=Xenium` 返回 2015 条 = 全表），页面看着像「查到了很多」，违反「拒绝优于静默」。
  现 `count=0` 且 `scope_note` 明确写「没解析出条件、没有执行筛选」并给可用问法示例。
- **年份认两位数（2026-09-18 修）**：`25年的社保` 与 `2025年的社保` 等价（期间条件不再被丢弃）。
  查询**自带期间**时，同类别里「无期间」的行不再混进结果。
- 条目**无期间值 ≠ 缺失**，表示它本身不含期间。

## 4A. `GET /api/three-modules` — 需求一 三类材料定位（2026-09-13 新增）

需求方明确**只做这三类**，括号内是每类必须识别出来的源信息：

| 模块 | 要识别的 | 数据源 |
|---|---|---|
| `项目业绩` | 哪个产品、合同金额、合同签订日期、**是否有收款凭证** | `contracts` + `contract_items` + 收款凭证台账 |
| `财务社保数据` | **包含什么月份** + **凭证合计金额**（`finance_amount`，2026-09-17 新增）| `material_facts`（`finance_period` / `social_security_month` / `finance_amount`）|
| `仪器设备清单` | 哪些仪器、是否有采购合同、发票、仪器照片 | `material_facts`（`instrument_name` / `instrument` / `purchase_contract` / `instrument_purchase_contract` / `invoice` / `instrument_photo`） |

```
GET /api/three-modules                        # 三模块概览（各自覆盖多少）
GET /api/three-modules?module=财务社保数据&limit=300
```

**必读语义（这几条是诚实性红线，接入方不得绕过）**

- **`payment_status` 是四态，不得压成布尔**：
  `yes`=台账记载有付款时间；`no`=台账**明确写「未到款」**；`unknown`=台账有该合同但未记付款；
  **`ledger_absent`=该合同根本不在台账里（≠ 没收钱，只是这批台账没覆盖它）**；
  **`receipt_file`=存在以该合同号命名的银行回单图片**（见 `receipt_files`，来自 `银行回单.zip` 的
  **中央目录**，**只读了文件名、未核内容**，故**不等于款项已到账**）。
  台账来自**另一个主体**，覆盖范围有限 —— 不得把 `ledger_absent` 展示成「无收款凭证」。
- **产品已归一**：`products[].canonical` 是产品族（`scripts/canonicalize_products.py`，411 个原始串 → 58 族）。
  响应里的 `product_summary` 直接回答「哪个产品」——每个产品族的合同数与合计金额。
  ⚠️ 归一**不合并不同产品**：`10x Genomics 单细胞转录组测序` 与 `…空间转录组测序` 是两个族
  （「10x Genomics」是**平台**不是产品）。
- **`role_scope` 必须展示**（`财务社保数据` / `仪器设备清单`）：
  `our`=我方响应/最终版（**这才是需求一问的「响应文件里有没有」**）；
  `tender`=**招标要求**（采购人要求提交的材料，**不等于我方已附**）；`other`=资质附件/过程材料/待复核。
  实测 `财务社保数据` 1,564 条里只有 623 条是 `our`、238 条是 `tender` —— 不区分就是把
  「招标文件要求交社保」说成「我方响应文件里有社保」。响应里另有 `our_count`/`tender_count`/
  `other_count` 三个计数，接入方**必须**把它们分开表述。
- **产品金额是「同产品明细行合计」**（计划 §5.3/D9），不是逐行金额，也不是合同总额。
  每条 `products[]` 带 `amount_known`（`false` = **金额未确认**，不是 0）、`detail_rows`、
  `zero_amount_rows`（文档**明写 0.00** 的赠送行，与「缺失」不同）、`derived`（由数量×单价推算）。
- **`contract_date` 有两种精度**：完整签署日（`YYYY-MM-DD`）与**合同编号年月**（`YYYY-MM`，代理值）。
  实测二者月份一致率仅约 53%，故 `YYYY-MM` **不得当作精确签署日**做时间过滤。
  （2026-09-13 修复后，98 份 CTL 合同里精确签署日已由 **15 → 47** 份；根因是 OCR 把签署页日期
  渲染成 `2024.9.20` 这类**点分隔**格式而抽取器只认「年月日」，日期一直在正文里。）
- `fact_value` 对 `instrument_name` 是**仪器名**，对其余材料类是**期间**；提不到时为空，**不是 0**。
- **`files` / `file_count` 与 `/api/material-facts` 同口径**（按文件折叠）：`财务社保数据` 与
  `仪器设备清单` 的明细按文件折叠，`fact_values` 列出该文件的全部期间。`records` 保留不变。
  ⚠️ 展示「几份文件」用 `file_count`，「几条记录」用原有计数 —— 混用会把一份文件的 4 个月说成 4 份文件。

## 4D. `GET /api/plan-outline` — 需求二：标题结构预览／自动填入（2026-09-18 新增）

**不生成、不检索、零外发**（纯本地解析，不调任何模型）：把用户那句话（或手选的大/小标题）
拆成 **大标题 + 小标题**结构返回，供页面**自动填入**生成用的结构框。
需求原文：「指定标题结构能不能自动化填入 —— 现在还需要用户自动填入」。

```
GET /api/plan-outline?q=售后服务方案，必须包含服务周期和应急预案   # 自然语言路径
GET /api/plan-outline?title=售后解决方案&sections=售后服务团队,售后服务方式  # 手选路径
```

**与 §5 生成的关系（同一份实现，不另写一套）**
- `?q=` 走的是 `app/proposal.py::plan_sections()` —— **与 `proposal-generate` 里"结构从 query 推"
  用的是同一个函数**，因此**预览到的结构与生成时实际生效的结构一致**。
- 生成时的结构优先级仍是：`request.outline`（手填）> 从 `query` 推 > 不约束（见 §5）。
  本端点只是把"从 query 推"这一步**提前给用户看**，**不替代**生成时的判断。

**响应**
```json
{
  "planned": true,
  "title": "售后服务方案",
  "sections": ["服务周期", "应急预案"],
  "section_modules": [{"name": "服务周期", "module": "售后方案"},
                      {"name": "应急预案", "module": "应急预案"}],
  "inferred": ["服务周期"],
  "dropped": [],
  "scope_note": "这是**标题结构预览**（零外发、不生成）：确认后再点「模型起草方案」。…"
}
```

| 字段 | 含义 |
|---|---|
| `planned` | **是否真拆出了结构**。`false` = 没拆出，**调用方必须如实告诉用户"没拆出结构"**，不要假装填上了（那会让用户以为结构生效、实际没有） |
| `title` | 大标题（**用户的原话长形**，如「售后服务方案」；拆不出为 `""`） |
| `sections[]` | 小标题名（**用户措辞**，顺序即生成时的顺序） |
| `section_modules[]` | 逐条归属模块 —— 召回按它走。**手选路径（`?title=&sections=`）下 `module` 恒为 `""`**（未推定，生成时再按词表判） |
| `inferred[]` | 归属模块**是系统推的**那些小标题名（它们不在方案模块词表里）。**必须展示给用户** —— 证据取自其归属模块的池子，不符时用户应改措辞 |
| `dropped[]` | 用户**点名但未被纳入**结构的小标题。**必须展示**（否则用户以为写进去了） |
| `scope_note` | 可直接上屏的中文说明（已含上面两类的告警文案） |

**必读语义**
- **`planned=false` 不是错误**，是如实回答；`?q=` 为空且没给 `title`/`sections` 时同样返回
  `planned=false`。
- 前端「手改优先」：用户编辑过结构框后，输入框的防抖自动填入**不再覆盖**手改内容（前端行为，
  服务端无状态）。接入方若自己做自动填入，建议同样处理。
- **无副作用**：不写库、不写文件、不产生任何外发；拆不出结构也**不阻断** §5 的生成。

## 5. `POST /api/proposal-generate` — 需求二：方案草稿

**只有一条路：`mode=llm`（模型起草）。** 2026-09-14 用户指令：需求二只保留模型生成，
本地拼装（`mode=local`）已从 API **下线**（传 `local` 会收到明确 400）。

| 项 | 行为 |
|---|---|
| 生成 | 模型起草：证据包 + 模块化经验 → 模型成文 |
| 外发 | **会把我方响应正文发往公司网关**（qwen3.7-flash） |
| 授权 | 需 `PROPOSAL_GEN_ENABLED=true`（`docs/authorizations/llm-generation-authorization.md` §9 已有记录） |

**请求**
```json
{"query": "售后服务方案，必须包含服务周期和应急预案"}
// 或缺省 mode（等价于 mode=llm）；或 {"modules": "售后方案,应急预案"}
// 可选：指定输出标题结构（2026-09-17 新增）——
//   对象形态：{"outline": {"title": "售后解决方案",
//                          "sections": ["售后服务团队", "售后服务方式", "整体技术支持服务方案", "服务质量承诺"]}}
//   Markdown 文本形态（同构，两种都收）：{"outline": "# 售后解决方案\n## 售后服务团队\n…"}
```

**`outline` 语义（2026-09-17 需求方第二次对接的需求2）**
- **要求模型逐字遵守**：大标题一级（`#`）、小标题二级（`##`）、**顺序一致、不得增删改名、不得自造小节**。
  提示词里下发硬性结构块（`app.proposal.format_outline_block`），`GEN_SYSTEM` 规则 7 相应改写。
- **只约束输出结构，不改变证据召回**（召回仍按 `MODULE_KEYWORDS` 的模块名走）。
  ⚠️ 因此给了 `outline` 时，校验器**跳过「模块名是否出现」那一项**（用户标题与模块名本就不同名，
  如「售后解决方案」vs「售后方案」，继续按模块名判必然误报），改为由 `_validate_outline` 逐字校验结构。
- **可选**：不传 = 不约束，行为与加此参数前**逐字节一致**（既有 300+ 测试零回归验证）。
- 校验漂移只**报不改写**（与既有校验器同一哲学）：缺小标题 / 大标题不符 / 出现结构外二级标题
  → 进 `validation`。**容忍模型自加序号**（`## 1、售后服务团队` 算命中，那是排版不是漂移）。
- 响应新增 `outline_used`（生效的结构；不传时为 `null`）。
- **结构可以「从 `query` 推」（2026-09-18 新增）** —— 用户不必手填文本框：
  `{"query": "售后服务方案，必须包含服务周期和应急预案"}` → 系统拆出
  **大标题 = 售后服务方案**、**小标题 = 服务周期 / 应急预案**，模型逐字按此输出。
  优先级：`request.outline`（手填）> 从 `query` 推 > **不约束**（拿不到就按模块自由成节）。
- 响应新增三个字段说明结构从哪来、推成了什么：

  | 字段 | 含义 |
  |---|---|
  | `outline_source` | `user`（手填）/ `query`（从查询推）/ `none`（未施加结构约束） |
  | `title_planned` | 推出来的大标题（**用户的原话长形**，如「售后服务方案」；推不出为 `""`） |
  | `sections_planned[]` | `{name, module, module_inferred?}` —— `name` 是**用户措辞**、`module` 是**归属模块**（召回按它走）。`module_inferred=true` 表示**归属是系统推的**（该小标题不在模块词表里，如「服务周期」），接入方应如实告知用户 |

- ⚠️ **「服务周期」这类词不在模块词表里**：它作为小标题**保留**（用户点名要的），
  证据取自归属模块（售后方案）的池子，并在 `sections_planned` 里标 `module_inferred`。
  实测：ES 里标题真正含「服务周期」的章节只有 1 条，单独立节几乎没有证据。
- ⚠️ **「未纳入结构」的告警按小标题粒度**（2026-09-18 修）：原先按「必须包含」整片段判定，
  `服务周期和应急预案` 里只要有一个模块命中就判「已认出」→ 片段里的另一项被**连带跳过、
  一条提示都没有**。现逐项核对，未纳入的逐条进 `warnings`。
- 外发面不变：`outline` 是**用户自己敲的标题文本**（无正文），仍在既有生成授权范围内。

**响应**
```json
{
  "mode": "llm",
  "markdown": "# 方案草稿 ...",
  "citations": [{"ref": "E1", "heading": "...", "file_name": "..."}],
  "warnings": [{"module": "应急预案", "slot": "响应", "values": ["10分钟", "4小时"],
                "sources": {"10分钟": ["E7"], "4小时": ["E8"]},
                "message": "「应急预案」的「响应」在不同历史文件里不一致：... 请人工确认，系统不自动择一"}],
  "gaps": [{"module": "...", "status": "sparse"}],
  "validation": [],
  "coverage": {"requested": 2, "ok": 2, "sparse": 0, "insufficient": 0},
  "modules": [...], "scope_note": "这是**草稿**，不是最终稿：..."
}
```

**必读语义（这几条是产品红线，接入方不得绕过）**
- `citations[].ref` 由**系统生成**，模型不得编造。`validation` 非空即表示检出编造引用／缺小节／
  数字无法回溯／**行文风格问题**，**必须逐条处理**再使用。
- **引用编号的括号形态，工具链一律认全角与半角**（2026-09-18 修）：`[E3]`、【E3】、［E3］、
  「E3」、（E3）都识别；**裸 `E3` 不认**（避免 `SE3`/`ACE3` 误匹配）。规范写法仍是**半角 `[E3]`**，
  且**放在句末** —— 逐条以「根据 Ex，」开头会让整篇读起来像检索日志（提示词已明确要求，
  `validation` 里也会如实提示，**只报不改写**）。
  接入方若自行渲染正文，引用正则需与此口径一致，否则编号会原样留在正文里。
- `warnings` 是**数值冲突**，系统**只告警、不自动择一**（`sources` 给出各自来源）。
- `gaps`／`coverage.sparse` 表示**证据不足**，正文里会写明"历史材料不足"。
  **不要**用常识补写。
- `mode` **必须展示给用户**——模型起草产物的可信度边界要讲清楚。

**错误**
- `403` 未授权（`PROPOSAL_GEN_ENABLED=false`）→ **不会有任何外发**。
- `400` 未知小节（`detail` 里会列出全部可选小节）。
- `400` `mode=local` → 已下线（2026-09-14 用户指令只保留模型生成）。
- `502` 模型生成调用失败（网关不可达 / 未返回内容）。

## 7. `POST /api/open` — 打开源文件 / 定位所在文件夹（2026-09-14 新增）

把结果卡片上的「复制文件位置（给IT定位用）」升级为**直接打开**。

```
POST /api/open
{"document_id": "<64 位十六进制>", "target": "folder" | "file"}
→ {"ok": true, "target": "folder", "file_name": "…",
   "message": "已交给资源管理器定位（没看到窗口的话，可能被其他窗口挡住）"}
```

**必读语义（安全设计，接入方不得绕过）**
- ⚠️ **只接受 `document_id`，绝不接受任何路径字段** —— 路径一律服务端从库里反查重建。
  这样「客户端提交任意路径」这一整类风险**从根上不存在**，而不是"接受路径再校验"。
- ⚠️ **只读语义不变**：只"打开/定位"，**不写、不改、不移动共享盘上的任何东西**。
- ⚠️ **会在服务端所在机器上启动外部程序**（`explorer` / 系统默认程序）。因此：
  **默认关闭**（`OPEN_EXTERNAL_ENABLED=false`），且默认只允许**回环**访问
  （`OPEN_EXTERNAL_ONLY_LOOPBACK=true`）。若集中部署，此端点的语义会变成
  "在服务器上开窗口" —— 那时应只保留前端本地的「复制路径」。
- ⚠️ `message` 只说**我们做了什么**（交给了外壳），**不说"已经打开了"** ——
  外壳的成败服务端核实不了，声称成功就是误导。

**拒绝码（逐条，理由为中文）**
| 码 | 场景 |
|---|---|
| `403` | 功能未开启（`OPEN_EXTERNAL_ENABLED=false`）／非回环访问 |
| `400` | `target` 非 `folder`/`file`；`document_id` 格式不合法；登记的相对路径含上级目录、非法字符、段尾点/空格、保留设备名；后缀在**黑名单**（`.exe .lnk .bat .ps1` 等）或 `target=file` 而后缀不在**白名单** |
| `404` | `document_id` 未登记；或文件已不在共享盘原位置（可能已改名/移走 → 建议重新检索） |
| `500` | `source_root_id` 未配置（服务端配置缺陷）；路径越界（内部一致性错误） |
| `503` | **共享盘当前不可达或无权限** —— 与 `404` **刻意分开**：一个是去连网络，一个是数据过时 |

**为什么黑名单是硬要求**：库内实测有 **6 个 `.exe`**（投标客户端安装包），
而 `os.startfile` 对 `.exe` 是**执行**而非"打开"。黑名单**先于**白名单判定，
且 `target=file` 的白名单**刻意排除宏格式**（`.docm/.xlsm/.pptm/.xlsb`，打开即可能执行宏）。

**回退**：`.env` 置 `OPEN_EXTERNAL_ENABLED=false` 即整功能下线；
代码级回退 = 删掉 `app/api.py` 底部 `include_router(_open_router)` 一行。

## 8. `POST /api/tender-check` — 招标要求核对（2026-09-14 实现，⚠️ **功能已暂停，接入方勿依赖**）

把**新**招标文件里的实质性条款（★/▲）与服务时限要求逐条抽出来，对照历史响应文件标出
「有先例 / 比历史都严 / 历史没覆盖」。**产物是核对清单，不是自动应答**。

**请求**（两种都收；手动读 body，不用 FastAPI 的 `File`/`Form` 声明 —— 那会强制 multipart，纯 JSON 调用方直接 400）
- `multipart/form-data`：`file`（`.docx` / `.pdf` / `.xlsx` / `.txt`）或 `text`
- `application/json`：`{"text": "…"}`

⚠️ **上传的文件不落库、不写 NAS**：读进内存解析一次即弃，解析全程本地（**零外发**）。

**响应**

| 字段 | 内容 |
|---|---|
| `source` | 输入来源名（文件名；粘贴文本时为「（粘贴的文本）」） |
| `checklist[]` | **全部** ★/▲ 实质性条款：`{seq, name, text, category, severity:"hard", pool_key, pool_note}` |
| `by_category` | 条款按类别计数 |
| `checklist_total` | 条款总数 |
| `requirements[]` | 服务时限要求：`{slot, slot_label, value, minutes, clause, mandatory, verdict, note, history[]}` |
| `summary` | `{total, mandatory, covered, stricter, uncovered}` |
| `scope_note` | 一句话结论（含上述计数 + 「材料池 ≠ 已满足」的提醒） |

**必读语义**
- **`pool_note` 是粗粒度线索**：「我司库里有 N 份这类材料可作响应依据」**不等于某一条要求已满足** ——
  具体某条（如「具备 CNAS 认证」）仍须人工打开文件核对。
- **`verdict` 三态只并列、不择一**：`covered`=有同等或更严的先例；`stricter`=**比历史任何一次都严**；
  `uncovered`=历史材料里没有对应承诺。后两种**必须人工确认能否做到**。
- ⚠️ **时限的依据是该项目的招标文件，不是历史响应文件**（2026-09-14 逐项目实测 43 个项目 / 111 条）：
  招标文件写了时限的 **56% 被逐字照抄**进响应文件、38% 同类改写。历史材料只是**模板与底账**
  （我们最多承诺过什么）—— **拿 A 项目的 48h 填 B 项目，若 B 要求 24h 就是废标风险**。
- **错误码**：`400` = 请求体为空（既无文件也无文本）／文件格式不支持（`detail` 给出后缀）。
