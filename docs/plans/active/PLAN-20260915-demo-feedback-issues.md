## 1. Problem and business outcome

需求方首次实机试用 `http://127.0.0.1:8000` 后反馈 5 个问题（需求一 4 条、需求二 1 条）。
它们不是"系统坏了"，而是**真实使用场景与当前实现口径的错配** —— 直接影响演示可信度与可采纳性。

业务目标：让需求方**按自己习惯的说法**查得到历史材料、拿到**与本产品线匹配**的方案草稿。

**逐条核实结论（先看原文、先验口径；与用户感知不完全一致处已标明）**：

| # | 用户反馈 | 核实结论 | 性质 |
|---|---|---|---|

## 2. Users and workflow

- **用户**：需求方（业务/投标同事），不写代码、按日常说法提问。
- **典型动作**：
  - 需求一：`空间转录组 50万以上的合同`、`华大转录组 30w 合同`、`找有质谱仪的合同`、`2025年的社保`。
  - 需求二：`单细胞转录组，应急管理措施`、`代谢组 质量控制方案` —— **先点产品线，再点方案名**。
- **成功标准**：按其习惯说法能查到/生成；查不到时**知道为什么**，而不是空白或含糊提示。

## 3. Scope

- **R1-1**：**明确并公示系统覆盖面**（Z 盘文档 vs 合同台账）；是否引入合同台账为数据源（重大范围决策）；`Visium HD`/`Stereo-seq` 等型号的产品归属（**需业务定**）。
- **R1-2**：社保/财务月份的抽取上下文收紧（授权书有效期等无关日期不得产出 fact）。
- **R1-3**：仪器**通称**（质谱仪/测序仪/流式细胞仪…）→ 具体型号的映射与检索；`instrument` 事实脏值清理。
- **R1-4**：支持「供应商名 + 产品 + 金额」自由组合的模糊检索。
- **R2-1**：方案生成引入**产品维度**（召回加权/过滤 + 提示词约束），并区分「产品通用小节」与「产品特异小节」。

- **R1-1.b′**（**2026-09-15 用户裁定：不纳入台账** → 改为本项）：
  **补齐 Z 盘语料内的合同提取覆盖** —— 用户指出「现在入库的 127 份合同**可能不全**」。

  **✅ 已盘点（2026-09-15，只读，未改数据）**：

  | 口径 | 数 |
  |---|---|
  | 文件名中出现的**不同合同号**（`BOE/YOE/ZOE/DZOE/YLM`+6位以上）| **135 个** |
  | `contracts` 表已登记的合同号 | **93 个** |
  | **缺口**（文件名有、库里没有）| **43 个** |

  **根因（与此前猜测不同）**：**不是数据源问题，是解析覆盖缺口** ——
  这 43 个合同号对应的合同文件**已经在库里登记**（角色 `contract_evidence`，样例
  `BOE2023081556-Illumina甲基化芯片检测-厦门大学附属第一医院-954,400.00.pdf`），
  但 **`parse_status = pending`（未解析）** → 从未被提取成 `contracts` 记录。
  - 关联文档 509 份（`contract_evidence` 503 / `process_material` 4 / `unknown` 2），其中 **478 份 pending**；
  - 39/43 有**非逐页图的主文档**（即确有一份合同原件，不是只有拆页图）。

  **附带发现**：`contracts` 里 127 条 = **98 个 `CTL-`**（文档解析）+ **29 个 `LEDGER-`**。
  `LEDGER-` 并非外部台账，而是**从响应文件里的「业绩清单/合作单位证明」表格抽出**的条目
  （无合同号、有甲方与金额，来自 4 份文档）—— 属另一条抽取路径，与合同原件不同源。

  **结论**：补齐路径 = **解析这 39–43 份合同原件 → 提取合同头/金额 → 进 `contracts`**。
  ⚠️ 合同扫描件 OCR **已在既有授权内**（`docs/authorizations/ocr-authorization.md`，`contract_evidence` 角色）。
  ⚠️ 与"接入台账"是两件事：本项**不外扩数据源**，只在既有语料内提高覆盖率。

  **✅ 工作量估算（2026-09-15 实测）**：待补的**合同主文档 49 份 / 70 MB**（已剔逐页图），其中
  | 状态 | 份数 | 说明 |
  |---|---|---|
  | **已有正文** | **37**（`scanned_ocr` 36 + `native_text` 1）| 零新增外发 |
  | 需先解析/OCR | **12** | 走既有 `contract_evidence` OCR 授权 |

  **❌ 但实测补提取失败（0 份）—— 根因是设计约束，不是脚本问题**：
  写了 `scripts/backfill_missing_contracts.py` 跑第一轮（37 份有正文），
  **37 份全部因「无服务明细行」跳过**。逐份看正文后确认：这些是
  **简式合同 / 技术开发（委托）合同 / 明细写在附件里**的类型，**正文根本没有服务明细表**：
  - `BOE2024114246`：「预算金额：675000 元，合同价：**248 元/例**。本项目为**单价合同**」→ 无明细表；
  - `YOE2024122075`：「服务的内容、要求…**详见合同附件**」→ 明细不在正文（**且语料里没有该附件文件**，
    实测同目录只有合同本身）；
  - `BOE2025102115`：技术开发（委托）合同**示范文本**（科技部印制）→ 无明细表。

  而 `CTL-` 合同是**明细锚定**的（`sync_contract_service_items` 只在解析出真实明细行时才建，
  这条闸是**刻意**的：避免空合同污染检索）。**且** `app/search.py` 的红线写明：
  > 金额状态由 `product_amount_status` 判定：unknown/conflict → **不正式命中**；
  > 只有 status='ok' 且**明细求和**≥阈值才 hit=True。**金额取自 `contract_items` detail 求和，
  > 绝不用 `contracts.total_amount`**。

  **所以：这 43 份合同按现有设计「无法参与产品金额检索」** —— 不是没提，是**没有可提的明细**。
  但 **35/37 份的合同头字段可提取**（编号/甲方/金额都对，如 `BOE2025112005 上海市胸科医院 720000`）。

  **⚠️⚠️ 进一步核实推翻了"A 可行"的判断 —— 真正的卡点是白名单，且只有一个约束**：

  `app/search.py` 的检索第一道闸就是 **`if not any(doc.document_id.startswith(pid) for pid in approved): continue`**
  —— 必须在 `data/approved_documents.json`（**95 份**）内。实测 **37 份缺口文档 0 份在白名单内**。
  而白名单的 `basis` 字段写明：**「已建 CTL 服务明细的合同（人工核准 2 份 + OCR 批量 93 份）」**。

  即整条链是**一个约束**：
  ```
  文档解析 → 抽出服务明细 → 建 CTL 合同 → 进白名单 → 才能被检索
                ↑ 这 43 份卡在这一步（无明细表）→ 无 CTL → 不在白名单 → 检索不到
  ```

  | 选项 | 合同表数字 | **能否被检索到（hit）** |
  |---|---|---|
  | **A. 只登记合同头** | 127 → 约 162 ✅ | ❌ **不能** —— 无明细 → `dataless` **且**不在白名单 |
  | **B. 维持现状** | 不变 | ❌ 不能（同上） |
  | **C. 单产品按文件名归因** | 同上 | ✅ **能** —— 产生明细行 → 建 CTL → **可进白名单** → 可命中 |

  **C 的可行性已实测**：`product_from_filename` 在 **35/37** 上识别出**唯一产品**
  （「真核有参转录组测序」「二代宏基因组测序（QDOE）」…），且这是**仓库既有且已被接受**的机制

  1. **金额红线**：无明细表的**单产品**合同，用合同总额作为该产品金额 —— 须新增可审计来源值

  **材料期间不得晚于「项目日期 + 3 个月」** —— 项目目录名自带 `YYYYMMDD` 登记日期；
  `margin_months=3` 留给「登记日 → 实际投标」的正常间隔（实测 23 例只差 1 个月，属正常）；
  取不到项目日期时**不筛**（宁可不筛，不可误删）。

验证：三条报告记录 → **`None`（不再编造）**；全库「社保月份晚于项目日期 >3 个月」→ **0 条**；
社保事实 1364 → **1210**（去掉的是伪造值）；`pytest` **257 passed**（+1 条守卫测试）。

**第四轮（2026-09-16 需求方：「不能只改个例，我列举的只是其中一部分；而且检索会返回很多相同文件」）**
—— 这轮**改规则、不改案例**：

**① 期间抽取改「分档」，不再用统一的 ±150 字窗口**（`app/extract.py::scan_periods_near(same_line=…)`）：
| 标记档 | 规则 | 为什么 |
|---|---|---|
| **强标记**（`社会保险费缴费记录`/`社会保障记录`）| 窗口 ±150 | 那是**记录表**，OCR 把表格列打散，期间与关键词常不同行 |
| **宽标记**（`社会保险`/`社保` 泛词）| **只取同一行** | 那多是**声明句**（`现附上自…至…我方缴纳的社会保险凭据`）|

**根因（审计得出，不是猜）**：统一窗口下，**窗口内约 650 条是「签署时间/日期」**
（`签署时间：2025年1月22日`），只有 0–49 字那批才是真声明期间 —— 即**规则本身就选错了上下文**。
本轮报告的例子（2025-12 项目报 `2026-01`）正是「要求句无日期、签署日期在别行」被窗口吃进来。

**② 检索结果按文件折叠**（`app/api.py::_fold_facts_by_file`）：
材料事实是**一条期间一行**（一份社保缴费记录表就有 4 个月 ⇒ 4 条），列表把同一份文件显示多次。
`/api/material-facts` 与 `/api/three-modules` 均**新增 `files` 字段**（期间收进 `fact_values`、带
`record_count`），**不动原有 `facts`/`records`**（向后兼容）；前端改用 `files` 渲染。
与既有 `_fold_by_contract`（R6-06 合同折叠）同一原则：业务要的是「**哪几份文件**能用」。

**全库验证**：社保事实 1210 → **925**（去掉的是签署日期等伪造值）；「社保月份晚于项目日期 >3 个月」
**0 条**；抽查折叠：`500 条事实行 → 496 份文件`，多期间文件如实并列（如 `['2024-08','2024-10','2025-02']`）。
`pytest` **259 passed**（+2 条守卫：同行规则、按文件折叠）。

**第五轮（2026-09-16 需求方追问两处，均为「规则漏洞」而非案例）**：

**(a) 「同一份文件多个月份」暴露的真问题是日期不准确**（需求方原话质疑，**判断正确**）：
记录表里有两类日期列 —— `费款所属期`（是**月**，如 `2026-04`，✅ 真正的社保月份）与
`入库日期`（是**具体日**，如 `2026-05-14`，❌ 缴款入库日）。实测该文件的「4 个月份」
**全部来自完整日期**（`2026-04-01`/`05-14`/`06-30`/`07-14`），其中还混进了**隔壁税收凭据段**的日期；
且该表 `费款所属期` 的值被 OCR 粘成 `2026-04206-04`，**无法可靠分离**。
→ 修法：记录表路径**只认「月」形态、不认完整日期**（`scan_periods_near(month_only=True)`）；
取舍是**该文件不再给出月份（期间未知）**—— 按"宁缺毋滥"，不给一个可能是入库日的值。
**"按文件折叠"只是展示层，不解决准确性问题** —— 需求方指出这一点是对的，两者都要做。

**(b) `质谱仪` 查不到、`测序仪` 可以** —— 根因在 `/api/ask` 的**路由词表**：
它用 `_ASK_FACT_KW`（派生自 `_FACT_KW`：`仪器/设备/测序仪`）判「该查哪一类」，
**`质谱仪` 不在表里** → 落到合同检索 → 被「仪器／设备条件」守卫拒绝。
（第四轮只改了 `material-facts` 端点，**没改 ask 的路由判断** —— 同类词全会掉进这个洞。）
→ 修法：`ask` **先问 `resolve_instrument_query`**（通称表 + 库内真实型号同源），不再依赖那份手写词表；
并给合同侧的仪器拒绝配上**可执行的出路话术**（指向「仪器设备清单」或型号名）。

验证：`质谱仪`→32 条 / `生物分析仪`→66 条 / `Bruker timsTOF HT`→8 条（此前 `质谱仪` 直接报错）；
多期间文件 **→1 份**（事实行 500 → 文件 498）；社保事实 925 → **913**；`pytest` **259 passed**。

**第六轮（2026-09-16 需求方：「只有合同定位能打开文件/文件夹，其他两类材料不行」）**：
