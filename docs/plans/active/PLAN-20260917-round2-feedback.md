## 1. 需求原文与业务目标

**痛点**：设备/合同/社保信息**原件都有**，但用户要的是「定位到文件里**整理后的、可以复制**的内容」——
现在检索只给登记行和文件名，不给可直接粘进标书的正文。

**需求方的启发**：把所有原件登记入库，检索时**先查登记的原件库，再去响应文件里定位**。
→ 核实：本仓库**已经是这个架构**——`documents`（6,043 份登记）+ `material_facts`（2,006 条事实行）
+ `contracts`（544 条）就是「原件登记库」；缺的只是最后一步「**从响应文件正文裁出可复制段落**」。
**不建新库、不加架构层**（红线：确定性规则 + SQLite 台账为主）。

**需求1**：仪器定位有问题；社保召回信息有问题；希望支持「纳税社保总金额」这类更灵活的检索。

**需求2**：LLM 输出**严格按给定标题结构**生成（例：大标题「售后解决方案」+ 四个小标题
「售后服务团队/售后服务方式/整体技术支持服务方案/服务质量承诺」），优化提示词约束模型输出。

## 4. 需求分解与方案

### R3-1 可复制正文段落（痛点主项）

**做法**：`material-facts` / `three-modules` 的每条返回增加 `content_snippet` ——
以 fact 行的锚点（`fact_value` 型号名 / 期间 / 关键词）在 `parse_artifacts.text` 里定位，
**裁出所在段落原样返回**（含前后各一段上下文，限长如 600 字），附 `snippet_source`（文件名+可打开路径）。
纯本地、零外发、零写库（查询时实时裁）。

- 锚点定位失败（正文找不到）→ `content_snippet=null` + 如实标注，不猜。
- 前端卡片加「复制」按钮（`navigator.clipboard`，纯静态 JS，无新依赖）。
- **非目标**：不做表格重排/字段化整理（第二阶段）；不改 evidence_text 既有语义。

### R3-2 仪器定位修复（D1）

**做法**（检索/展示层，不动库）：
1. `three-modules` 仪器设备清单与 `material-facts` 排序：**有型号/有内容的行优先，空壳行沉底**并标注
   「该文件登记了仪器材料，但未抽出型号明细（可打开原文核对）」；
2. 空壳行借 R3-1 的 `content_snippet` 补上可复制正文（211 条 instrument 空壳行的文档都有正文可裁）；
3. 仪器查询词映射不动（`resolve_instrument_query` 三路命中已是修好的，实测「找质谱仪」返回型号行正常）。

### R3-3 纳税社保总金额（D3）

**做法**：
1. **新增 fact_type `finance_amount`**（覆盖社保缴费金额与纳税金额，`fact_value` 存数值字符串，
   `evidence_text` 存含金额的原文行）——抽取走**离线脚本**（`scripts/backfill_finance_amounts.py`，
   只写 `bid_ai_clean_reg.db`，正式库禁写红线不变；只增不删）；
2. 抽取判据**保守**（宁缺毋滥红线）：只认「合计/金额/总额 + 数字 + 元」同现的行，且文档文件名或
   正文含社保/完税标记；**抽不到不猜**、不推算；同一文档多个金额并存时全部入库、并列不择一；
3. `_FACT_KW` 加映射：「总金额/总额/多少钱」+（社保|纳税|完税）→ `finance_amount`；
   `parse_fact_query` 支持「纳税社保总金额」这类问法；
4. 返回行带 `amount_note`（口径说明：这是**凭证上的合计金额**，非合同金额，不参与任何合同金额筛选）。

**验收**：「纳税社保总金额」查询返回金额行；抽样 10 条人工核对 evidence 与金额一致；
抽不到的文档如实为 0 条（不硬凑）。

### R3-4 生成标题结构约束（D5，需求2）

**做法**：
1. `POST /api/proposal-generate` 请求体加 **`outline`** 参数：
   `{"title": "售后解决方案", "sections": ["售后服务团队", "售后服务方式", "整体技术支持服务方案", "服务质量承诺"]}`
   （也接受同构的 Markdown 文本，解析成同一结构）；不传 = 现行为不变（向后兼容）；
2. `build_gen_prompt`：outline 存在时注入**硬性结构块**——「大标题必须逐字为 {title}（一级标题）；
   小标题必须逐字使用下列四个（二级标题）、顺序一致、**不得增删改名**；每个小标题下的内容仍受
   证据与引用规则约束」；`GEN_SYSTEM` 规则 7 相应改写；
3. `validate_generation` 加 **outline 校验**：缺任一小标题 / 大标题不符 / 出现 outline 外的自造二级标题
   → 如实报入 `validation`（只报不改写，与现校验器同一哲学）；
4. 前端：生成入口加 outline 输入（大标题 + 小标题逐行），示例按钮带一个售后 outline 演示；
5. **外发面不变**：outline 是用户敲的标题文本（无正文），仍在既有
   `llm-generation-authorization.md` 授权范围内，**无需新授权**；`PROPOSAL_GEN_ENABLED` 默认 false 不变。

**验收**：传示例 outline 生成 → 输出大/小标题逐字一致（模型偶发漂移时 `validation` 必须报出来）；
不传 outline 的既有测试全部不回归。
