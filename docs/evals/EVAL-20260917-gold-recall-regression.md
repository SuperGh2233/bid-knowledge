## 3. 根因：**方案 C 的单产品归因，只在检索侧生效，没同步到 `contract_items`**

漏掉的 5 份逐个定性（全部**在库、在白名单、指纹一致、资格门槛全通过**，但**一条 LocateResult 都没有**）：

| 合同 | 明细行 `product_raw` | 为什么该命中「代谢组」 |
|---|---|---|
| YOE2024021181 | `全基因组重测序（人类）/`（服务名**空**）| 正文写「…基因组重测序…蛋白组学…**代谢组学检测**和数据分析」——合同**含代谢** |
| YOE2024080476 | `10× Visium CytAssist 冰冻样本空间转录组测序/`（空）| 正文写「18 例冰冻样本进行**空间转录组及代谢组**测序」 |
| YOE2024082739 | `多组学检测（非范本合同）/`（空）| 正文含「**空间代谢组学分析**」（21 处「代谢」）|
| BOE2025110208 | `多组学检测（非范本合同）/`（空）| 同上（多组学）|
| YOE2025010758 | `Pro DIA定量蛋白质组/…`（**蛋白**产品）| 金标准标它 relevant「代谢组」，但产品是蛋白组 —— **语义存疑** |

**`product_raw` 是「类别/服务名」，这 5 份的**服务名段全为空**（解析器在 proc 型/简式合同上解析不出服务名）
→ 服务名匹配路径必然落空；而**类别**是 `多组学检测（非范本合同）` 等**不含「代谢」**的字面
→ 类别路径也落空 → **`keys` 为空 → 一条结果都不产出**。

**关键对照**：这 5 份**恰恰是方案 C（`filename_product_total`）覆盖的那批** ——
`contract_items` 里已按「文件名唯一产品 × 合同总额」写入合成明细（如 `全基因组重测序（人类）`），
但那个产品名**不含「代谢」**，所以即使走到取明细那一步也匹配不上。

## 4. 两个口径问题（都已量化）

1. **方案 C 只解决了「金额」的一半问题**：它让单产品合同**有了金额**，但产品键仍是**文件名里的那个产品**
   （`10× Visium CytAssist 冰冻样本空间转录组测序`），**不是合同正文里真实包含的多个产品**。
   实测：**分母 59 条里 22 条（37%）属于方案 C 归因的合同** —— 这是 Recall 的系统性缺口。
2. **金标准本身有一条语义存疑**：`YOE2025010758`（`Pro DIA定量蛋白质组`）在 G01/G03/G04 标 relevant「代谢组」，
   而其产品是**蛋白组**。金标准把「含代谢的**多组学**合同」都算作代谢组相关 —— 与检索侧「产品对得上才算」的口径不同。
