## 为什么评

需求二的产品承诺是「方案名 + 必须包含什么 → 一份**带出处、可逐句回溯**的方案草稿」。
机器已保证的部分（每份样本的 `meta.json` 已列）：必要小节全覆盖、引用编号必带、不可追溯数字 0、
冲突只并列不择一、证据不足必显式说明。**机器保证不了的只有一件事，也只有人评得了：**
这份草稿拿给需求方/评审组，**像不像一份能用的方案、有没有专业硬伤**。这是本轮评审的唯一焦点。

## 怎么读

打开 `report.md`，随读随记。每个样本的 `meta.json` 是它的"体检单"。

## 判定标准（六项，逐项 ✓/✗/待议）

| # | 判什么 | 怎么判 | 判定 |
|---|---|---|---|
| 1 | **内容完整性** | 「必须包含」里点名的每节正文里都有？单模块方案的每一节不是空话套话？ | |
| 2 | **引用可回溯** | 全文每一段都能看到一个 `[E1]` 式编号（`meta` 里 `refs` 非空）？ | |
| 3 | **数字有出处** | 每一个承诺数字（**24h、30 分钟、7 个工作日…**）边上都带引用编号，没有裸数字？ | |
| 4 | **冲突如实并列** | 值不同时（`meta` 里 `warnings` 含"不一致"）两个值都列出 + 明确"请人工确认"？**有没有偷偷替决策挑了一个**？ | |
| 5 | **边界诚实** | 该说不够时说了？告警（比如「质控要求未纳入」）是不是一眼可见，没藏在角落？ | |
| 6 | **成文质量** ⭐ | 结构是否像正式投标方案的对应小节？语言通顺、专业术语用得对不对？**如果这是你要递给甲方的那一章，会不会被问倒？** | |

**第 6 项是本次评审的核心**，1–5 已经由程序和 test 保证，只是请你复核一遍免得有漏网。
真发现问题，请优先在第 3/4/6 项上写**具体**：「24h 这个数字的来源是哪份文件？我看了一下文内是 A 项目承诺的，B 项目招标要求可能是 24 小时，这里会不会造成废标风险」比「有点不对」有用一百倍。

## 填法

`outputs/proposal-quality-review-<时间戳>/review_record.md`（空表）：

```
样本            完整性  引用  数字  冲突  诚实  成文质量  备注
01-培训方案      ✓/✗   ✓/✗  ✓/✗  ✓/✗  ✓/✗   1-5分   …
…
```

- 六项全 ✓、成文质量 ≥4 → 该样本可作正面示例。
- 任一项 ✗ 或成文质量 ≤2 → 记下**具体位置**（复制那句话），这是要回修的证据。
- 收尾在备注里写一句总评价：**这套草稿到底能不能给需求方当"可直接编辑的初稿"用**。
